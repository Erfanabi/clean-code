# تمرین پیشرفته — درس ۸: Clean Code در برابر Clean Architecture

> درس مرتبط: [Clean Code در برابر Clean Architecture](../../../docs/00-foundations/08-clean-code-vs-clean-architecture.md)

## تمرین: «لغو سفارش» از دو کانال، و یک تصمیم مستند

**قواعد کسب‌وکار:**

- سفارش فقط در وضعیت‌های `pending` و `paid` قابل لغو است؛ `shipped` و `delivered` نه.
- اگر سفارش `paid` باشد، باید بازپرداخت از طریق درگاه پرداخت درخواست شود.
- اگر بازپرداخت شکست بخورد، سفارش **نباید** لغو شود و خطا باید گزارش شود.
- بعد از لغو موفق، موجودی کالاها به انبار برمی‌گردد.
- لغو هم از API وب و هم از پنل پشتیبانی (یک CLI ساده) ممکن است.

**خواسته:**

1. ساختار چهارلایه‌ی درس را پیاده کن: `domain`، `application`، `infrastructure` (فقط درون‌حافظه‌ای)، `presentation` (یک Handler شبیه‌سازی‌شده‌ی HTTP و یک تابع CLI که هر دو **همان** Use Case را صدا می‌زنند).
2. ترتیب عملیات در شکست را دقیق طراحی کن: اگر بازپرداخت موفق شد ولی برگرداندن موجودی شکست خورد چه؟ تصمیمت را بنویس.
3. تست‌ها: همه‌ی وضعیت‌ها، شکست بازپرداخت، و اینکه هر دو کانال رفتار یکسان دارند.
4. **ADR:** یک سند تصمیم معماری کوتاه (Architecture Decision Record) بنویس با بخش‌های: زمینه، تصمیم، پیامدها، و **«در چه شرایطی این تصمیم اشتباه است»**. صادق باش: آیا برای این مسئله، مرحله‌ی ۱ کافی نبود؟

**معیار پذیرش:** هیچ فایلی در `domain` چیزی از لایه‌های دیگر import نمی‌کند؛ یک تست این را با خواندن importهای فایل‌ها بررسی کند (امتیاز اضافه).
