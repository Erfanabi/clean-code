# درس ۱: Clean Code چیست؟ (What is Clean Code?)

> ماژول ۰۰ — مبانی Clean Code · [فهرست ماژول](README.md) · درس بعد: [ویژگی‌های کد تمیز](02-characteristics-of-clean-code.md)

## مقدمه

تصور کن شش ماه پیش یک فرم ثبت سفارش در پروژه‌ی React نوشته‌ای. امروز مدیر محصول می‌گوید: «تخفیف مشتری‌های طلایی از ۲۰ درصد به ۲۵ درصد تغییر کند و هزینه‌ی ارسال برای شهرستان‌ها متفاوت شود.» فایل را باز می‌کنی و با تابعی به نام `calc` روبه‌رو می‌شوی که پارامترهایش `o` و `t` هستند و عدد `0.2` وسط یک `if` نشسته است. ده دقیقه طول می‌کشد فقط بفهمی `t == 2` یعنی «مشتری طلایی». بعد نمی‌دانی آیا همین عدد جای دیگری هم تکرار شده یا نه. تغییرِ «یک خطی» تبدیل می‌شود به یک ساعت استرس.

این تجربه، دقیقاً مسئله‌ای است که Clean Code حل می‌کند. Clean Code درباره‌ی «زیبایی» یا «سلیقه» نیست؛ درباره‌ی این است که **هزینه‌ی فهمیدن و تغییر دادن کد** را پایین نگه داریم. چون در عمر واقعی یک نرم‌افزار، کد یک بار نوشته می‌شود و صدها بار خوانده و تغییر داده می‌شود.

## اهداف یادگیری

در پایان این درس باید بتوانم:

- تعریفی دقیق و قابل‌دفاع از Clean Code ارائه دهم.
- توضیح دهم چرا «کدی که کار می‌کند» کافی نیست.
- هزینه‌ی اقتصادی کد کثیف را برای یک مدیر غیرفنی توضیح دهم.
- در یک قطعه کد، نشانه‌های اصلی کد غیرتمیز را پیدا کنم.
- تفاوت Clean Code با «کد کوتاه»، «کد هوشمندانه» و «کد بهینه» را توضیح دهم.

## ۱. مفهوم اصلی

### تعریف

**Clean Code کدی است که یک توسعه‌دهنده‌ی دیگر (یا خودِ شش ماه بعدِ تو) بتواند آن را سریع بخواند، درست بفهمد و با اطمینان تغییر دهد.**

این تعریف سه جزء دارد که هر سه لازم‌اند:

1. **سریع خواندن (Readability):** خواننده برای فهمیدن نیت کد لازم نیست کد را در ذهنش «اجرا» کند.
2. **درست فهمیدن (Clarity):** کد خواننده را گمراه نمی‌کند؛ نام‌ها همان کاری را می‌گویند که کد انجام می‌دهد.
3. **با اطمینان تغییر دادن (Changeability):** تغییر در یک جا، چیزی را در جای غیرمنتظره نمی‌شکند و تست‌ها این اطمینان را پشتیبانی می‌کنند.

Robert C. Martin در کتاب Clean Code نظر چند مهندس برجسته را جمع کرده است. خلاصه‌ی مشترک همه‌ی آن تعریف‌ها این است: کد تمیز **ساده و مستقیم** است، **یک کار را خوب انجام می‌دهد**، **نیت نویسنده را آشکار می‌کند** و به نظر می‌رسد **کسی که آن را نوشته به آن اهمیت داده است**.

### تاریخچه‌ی کوتاه

- دهه‌ی ۷۰ و ۸۰: بحث «برنامه‌نویسی ساخت‌یافته» (Structured Programming) و مقاله‌ی معروف Dijkstra علیه `goto` اولین تلاش‌ها برای «قابل فهم کردن» کد بودند.
- ۱۹۹۹: کتاب Refactoring نوشته‌ی Martin Fowler مفهوم Code Smell را معرفی کرد. در همان سال The Pragmatic Programmer مفاهیمی مثل DRY و Broken Windows را رایج کرد.
- ۲۰۰۸: کتاب Clean Code نوشته‌ی Robert C. Martin (معروف به Uncle Bob) اصطلاح Clean Code را عمومی کرد.
- ۲۰۱۸: John Ousterhout در A Philosophy of Software Design دیدگاه متفاوتی ارائه داد: دشمن اصلی «پیچیدگی» است و بعضی توصیه‌های Clean Code (مثل توابع خیلی کوچک) اگر افراطی اجرا شوند، خودشان پیچیدگی می‌سازند.

نتیجه: Clean Code یک «مذهب» با قوانین ثابت نیست؛ مجموعه‌ای از اصول تجربی است که هدف مشترکی دارند: **کم کردن هزینه‌ی فهم و تغییر**.

### Clean Code چه مسئله‌ای را حل می‌کند؟

در یک پروژه‌ی واقعی:

- زمانی که صرف **خواندن** کد می‌شود، چندین برابر زمانی است که صرف **نوشتن** آن می‌شود. Robert C. Martin این نسبت را بیش از ۱۰ به ۱ تخمین می‌زند.
- بیشتر هزینه‌ی یک نرم‌افزار بعد از اولین انتشار و در مرحله‌ی **نگهداری و توسعه** خرج می‌شود.
- کد کثیف سرعت تیم را به‌تدریج کم می‌کند: هر فیچر جدید کندتر از قبلی تحویل می‌شود، چون باید از میان پیچیدگی‌های قبلی عبور کرد.

Martin Fowler این پدیده را در مقاله‌ی Design Stamina Hypothesis توضیح می‌دهد: در کوتاه‌مدت، بی‌توجهی به طراحی سریع‌تر به نظر می‌رسد، اما بعد از مدتی کوتاه (معمولاً چند هفته، نه چند سال) منحنی‌ها جابه‌جا می‌شوند و تیمی که کد تمیز نوشته جلو می‌افتد.

### ارتباط با سایر اصول

Clean Code «چتر» بسیاری از مفاهیمی است که در این بوت‌کمپ می‌بینی:

| مفهوم | ارتباط با Clean Code | ماژول |
|---|---|---|
| نام‌گذاری | اولین ابزار آشکار کردن نیت | ۰۱ |
| توابع کوچک و تک‌مسئولیتی | واحدهای قابل فهم و قابل تست | ۰۲ |
| مدیریت خطا | جدا کردن مسیر خوشحال (Happy Path) از مسیر خطا | ۰۴ |
| SOLID | Clean Code در سطح کلاس و ماژول | ۰۷ |
| Refactoring | روش تبدیل کد کثیف به کد تمیز بدون شکستن آن | ۱۱ |
| تست | شبکه‌ی ایمنی که تغییر با اطمینان را ممکن می‌کند | ۱۲ |

## ۲. توضیح فنی: Clean Code در عمل چطور شناخته می‌شود؟

تعریف بالا انتزاعی است. در عمل، کد تمیز این نشانه‌های قابل مشاهده را دارد:

- **نام‌ها نیت را می‌گویند:** `calculateOrderTotal` به‌جای `calc`، `customerTier` به‌جای `t`.
- **هر تابع یک کار انجام می‌دهد** و در یک سطح انتزاع (Level of Abstraction) باقی می‌ماند.
- **هیچ عدد یا رشته‌ی «جادویی» بی‌نامی وجود ندارد:** `FREE_SHIPPING_THRESHOLD` به‌جای `500000`.
- **Side Effectها آشکارند:** تابعی که اسمش «محاسبه» است، چیزی چاپ نمی‌کند و داده‌ای را تغییر نمی‌دهد.
- **نوع‌ها دقیق‌اند:** به‌جای `any`، ساختار داده صریحاً تعریف شده است.
- **تکرار وجود ندارد:** هر قاعده‌ی کسب‌وکار در یک جا تعریف شده است.
- **تست دارد** و تست‌ها مستندات رفتار هستند.

### Clean Code چه چیزی نیست؟

این بخش به اندازه‌ی تعریف مهم است، چون بیشتر سوءبرداشت‌ها از اینجا می‌آیند:

| تصور غلط | واقعیت |
|---|---|
| کد تمیز یعنی کد کوتاه | کد کوتاه و فشرده (مثلاً یک خط با سه ternary تودرتو) اغلب **ناخواناتر** است. معیار، زمانِ فهم است نه تعداد خط. |
| کد تمیز یعنی کد هوشمندانه | ترفندهای زیرکانه خواننده را مجبور می‌کنند متوقف شود و فکر کند. کد تمیز «خسته‌کننده» و قابل پیش‌بینی است. |
| کد تمیز یعنی استفاده از Design Pattern | استفاده‌ی بی‌مورد از الگوها پیچیدگی اضافه می‌کند (درس ۹). |
| کد تمیز یعنی کد کند | در اکثر موارد تفاوت کارایی قابل اندازه‌گیری نیست. بهینه‌سازی را بعد از اندازه‌گیری انجام بده. |
| کد تمیز یعنی وقت اضافه | در کوتاه‌ترین مقیاس شاید؛ ولی در مقیاس هفته‌ها، کد تمیز **سریع‌تر** است. |

### Trade-offها

Clean Code رایگان نیست و باید بدانی کجا ارزش دارد:

- **کد یک‌بارمصرف** (اسکریپت مهاجرت داده که یک بار اجرا و حذف می‌شود) نیازی به همان سطح دقت کد هسته‌ی محصول ندارد. اما مراقب باش: خیلی از کدهای «موقت» سال‌ها زنده می‌مانند.
- **نمونه‌ی اولیه (Prototype)** برای آزمودن یک ایده می‌تواند کثیف باشد، به شرط اینکه **واقعاً دور ریخته شود** و نه اینکه مستقیماً به Production برود.
- **زیاده‌روی** هم هزینه دارد: شکستن یک تابع ۱۵ خطی خوانا به ۷ تابع ۲ خطی، خواننده را مجبور می‌کند بین ۷ نقطه پرش کند.

## ۳. مثال اشتباه (Bad Code)

سناریو: محاسبه‌ی مبلغ نهایی یک سفارش در یک فروشگاه اینترنتی. مشتری‌ها سه سطح دارند (عادی، نقره‌ای، طلایی) با تخفیف ۰، ۱۰ و ۲۰ درصد. اگر مبلغ بعد از تخفیف بیشتر از ۵۰۰ هزار تومان باشد ارسال رایگان است، وگرنه ۳۰ هزار تومان هزینه‌ی ارسال اضافه می‌شود.

## ۴. تحلیل خط‌به‌خط کد بد

| خط | کد | مشکل |
|---|---|---|
| ۱ | `function calc(o, t)` | نام تابع نمی‌گوید «چه چیزی» را محاسبه می‌کند. `o` و `t` هیچ معنایی ندارند؛ خواننده باید کل بدنه را بخواند تا بفهمد `t` سطح مشتری است. |
| ۱ (TS) | `o: any, t: number` | `any` تمام مزیت TypeScript را از بین می‌برد. اگر کسی `o.item` (بدون s) بنویسد، کامپایلر چیزی نمی‌گوید. `t: number` اجازه می‌دهد `7` یا `-1` هم پاس داده شود. |
| ۲ | `var r = 0` | `var` دامنه‌ی تابعی دارد و منبع باگ‌های قدیمی است. `r` نام بی‌معنایی است؛ این متغیر در طول تابع سه معنای مختلف می‌گیرد: جمع اقلام، مبلغ بعد از تخفیف و مبلغ نهایی. |
| ۳–۵ | حلقه‌ی `for` با `o.items[i].p` | `p` و `q` مخفف‌های مبهم‌اند (price؟ points؟). حلقه‌ی دستی با اندیس، نیت «جمع زدن» را پنهان می‌کند. |
| ۶–۷ | `if (t == 1) ... 0.1` | سه مشکل هم‌زمان: (۱) عدد جادویی `1` به‌جای «نقره‌ای»، (۲) عدد جادویی `0.1`، (۳) مقایسه‌ی `==` که تبدیل نوع ضمنی انجام می‌دهد (`'1' == 1` درست است). |
| ۸–۱۰ | `if (r > 500000) { // free } else` | یک بلوک خالی با کامنت به‌جای شرط معکوس. `500000` و `30000` اعداد جادویی هستند. |
| ۱۱ | `console.log(...)` | تابعی که قرار است «محاسبه» کند، Side Effect دارد. در سرور لاگ اضافه تولید می‌کند و در تست خروجی را کثیف می‌کند. |
| کل تابع | — | چهار مسئولیت در یک تابع: جمع اقلام، اعمال تخفیف، محاسبه‌ی ارسال، لاگ کردن. تغییر هر کدام، ریسک شکستن بقیه را دارد. |

### مشکلات این پیاده‌سازی به زبان کسب‌وکار

- **تغییر نرخ تخفیف** نیاز به پیدا کردن عدد `0.2` دارد. آیا این عدد جای دیگری هم هست؟ معلوم نیست.
- **اضافه کردن سطح جدید** (مثلاً «الماسی») یعنی اضافه کردن یک `if` دیگر با عدد جادویی `3`.
- **تست نوشتن** سخت است، چون `console.log` خروجی تست را آلوده می‌کند و ورودی‌ها هیچ قراردادی ندارند.
- **Code Review** کند است، چون بازبین باید کد را در ذهنش اجرا کند.

## ۵. پیاده‌سازی صحیح (Clean Code)

```typescript
// TypeScript — Clean implementation
export type CustomerTier = 'regular' | 'silver' | 'gold';

export interface OrderItem {
  readonly unitPrice: number; // in Toman
  readonly quantity: number;
}

export interface Order {
  readonly items: readonly OrderItem[];
  readonly customerTier: CustomerTier;
}

const DISCOUNT_RATE_BY_TIER: Record<CustomerTier, number> = {
  regular: 0,
  silver: 0.1,
  gold: 0.2,
};

const FREE_SHIPPING_THRESHOLD = 500_000;
const SHIPPING_COST = 30_000;

function calculateSubtotal(items: readonly OrderItem[]): number {
  return items.reduce((sum, item) => sum + item.unitPrice * item.quantity, 0);
}

function applyTierDiscount(amount: number, tier: CustomerTier): number {
  return Math.round(amount * (1 - DISCOUNT_RATE_BY_TIER[tier]));
}

function calculateShippingCost(amountAfterDiscount: number): number {
  return amountAfterDiscount > FREE_SHIPPING_THRESHOLD ? 0 : SHIPPING_COST;
}

export function calculateOrderTotal(order: Order): number {
  const subtotal = calculateSubtotal(order.items);
  const discountedAmount = applyTierDiscount(subtotal, order.customerTier);
  return discountedAmount + calculateShippingCost(discountedAmount);
}
```

```javascript
// JavaScript — Clean implementation
const DISCOUNT_RATE_BY_TIER = Object.freeze({
  regular: 0,
  silver: 0.1,
  gold: 0.2,
});

const FREE_SHIPPING_THRESHOLD = 500_000;
const SHIPPING_COST = 30_000;

function calculateSubtotal(items) {
  return items.reduce((sum, item) => sum + item.unitPrice * item.quantity, 0);
}

function applyTierDiscount(amount, tier) {
  const discountRate = DISCOUNT_RATE_BY_TIER[tier];
  if (discountRate === undefined) {
    throw new Error(`Unknown customer tier: ${tier}`);
  }
  return Math.round(amount * (1 - discountRate));
}

function calculateShippingCost(amountAfterDiscount) {
  return amountAfterDiscount > FREE_SHIPPING_THRESHOLD ? 0 : SHIPPING_COST;
}

export function calculateOrderTotal(order) {
  const subtotal = calculateSubtotal(order.items);
  const discountedAmount = applyTierDiscount(subtotal, order.customerTier);
  return discountedAmount + calculateShippingCost(discountedAmount);
}
```

### تحلیل پیاده‌سازی صحیح

**۱. نوع‌ها قرارداد را صریح می‌کنند.** `CustomerTier` یک Union Type است: فقط سه مقدار مجاز دارد. حالا `calculateOrderTotal({ ..., customerTier: 'diamond' })` در زمان کامپایل خطا می‌دهد. به این ایده می‌گوییم «حالت‌های نامعتبر را غیرقابل‌نمایش کن» (Make illegal states unrepresentable) که در ماژول ۰۶ عمیق‌تر می‌بینیم.

**۲. `readonly` نیت را اعلام می‌کند.** این تابع سفارش را تغییر نمی‌دهد و نوع‌ها این را تضمین می‌کنند.

**۳. داده به‌جای شرط.** `DISCOUNT_RATE_BY_TIER` یک جدول است. اضافه کردن سطح «الماسی» یعنی یک خط در Type و یک خط در جدول. و چون نوع جدول `Record<CustomerTier, number>` است، اگر سطح جدید را به Type اضافه کنی ولی در جدول فراموش کنی، **TypeScript خطا می‌دهد**. کامپایلر به بازبین کد تبدیل شده است.

**۴. ثابت‌های نام‌دار.** `FREE_SHIPPING_THRESHOLD` هم معنی عدد را می‌گوید و هم تنها جایی است که باید عوض شود. `500_000` با جداکننده‌ی عددی (Numeric Separator از ES2021) خواناتر از `500000` است.

**۵. هر تابع یک کار و یک نام دقیق.** تابع اصلی `calculateOrderTotal` مثل یک «فهرست مطالب» خوانده می‌شود: جمع اقلام را حساب کن، تخفیف را اعمال کن، هزینه‌ی ارسال را اضافه کن. اگر جزئیات یکی را بخواهی، فقط همان تابع را باز می‌کنی.

**۶. بدون Side Effect.** هیچ `console.log`ی وجود ندارد. این تابع یک **Pure Function** است: ورودی یکسان، خروجی یکسان. تست کردنش ساده است. اگر لاگ لازم باشد، فراخواننده (مثلاً لایه‌ی API) تصمیم می‌گیرد.

**۷. `Math.round`.** محاسبه با اعداد اعشاری در JavaScript دقیق نیست (`0.1 + 0.2 !== 0.3`). در محاسبات مالی گرد کردن در نقطه‌ی مشخص، یک تصمیم آگاهانه است. در پروژه‌های جدی‌تر، مبالغ را به‌صورت عدد صحیح در کوچک‌ترین واحد پول (مثلاً ریال) نگه می‌داریم.

**۸. در نسخه‌ی JavaScript** چون Type وجود ندارد، با یک بررسی صریح (`discountRate === undefined`) سطح ناشناخته را **سریع و با پیام واضح** رد می‌کنیم (اصل Fail Fast، ماژول ۰۸). در نسخه‌ی TypeScript این بررسی را کامپایلر انجام داده است.

## ۶. مقایسه‌ی دو پیاده‌سازی

| معیار | Bad Code | Clean Code |
|---|---|---|
| زمان فهم برای خواننده‌ی جدید | چند دقیقه، با اجرای ذهنی کد | چند ثانیه؛ تابع اصلی مثل یک جمله خوانده می‌شود |
| تغییر نرخ تخفیف | جست‌وجوی عدد `0.2` در کل پروژه | تغییر یک مقدار در جدول |
| اضافه کردن سطح جدید | `if` جدید + عدد جادویی جدید | یک خط در Type + یک خط در جدول؛ کامپایلر فراموشی را می‌گیرد |
| ایمنی نوع | `any`؛ هر چیزی پذیرفته می‌شود | ورودی‌های نامعتبر در زمان کامپایل رد می‌شوند |
| تست‌پذیری | Side Effect و ورودی بی‌قرارداد | Pure Function؛ هر جزء جداگانه قابل تست |
| تعداد خطوط | کمتر | بیشتر — و این **اشکالی ندارد** |

نکته‌ی مهم ردیف آخر: نسخه‌ی تمیز **طولانی‌تر** است. Clean Code برای کم کردن خطوط نیست؛ برای کم کردن **بار ذهنی** است.

در Next.js این مسئله حیاتی‌تر است: قیمت نهایی باید **در سرور** دوباره محاسبه شود (هرگز به عدد ارسالی از مرورگر اعتماد نکن). وقتی منطق در یک Pure Function جدا باشد، همان کد هم در Client Component برای نمایش و هم در Server Action برای ثبت نهایی استفاده می‌شود؛ بدون تکرار.

## ۸. اشتباهات رایج

1. **«اول کار کند، بعداً تمیزش می‌کنم.»** «بعداً» تقریباً هیچ‌وقت نمی‌رسد. Kent Beck می‌گوید: Make it work, make it right, make it fast — اما «right» بخشی از همان کار است، نه یک فاز جدا در آینده‌ی نامعلوم.
2. **یکی دانستن تمیز با کوتاه.** جایگزین کردن یک `if` خوانا با `&&` و `||` زنجیره‌ای، کد را کوتاه‌تر ولی کثیف‌تر می‌کند.
3. **کامنت به‌جای نام خوب.** `// t is customer tier` نشانه‌ی این است که نام `t` اشتباه است. نام را درست کن، کامنت لازم نمی‌شود.
4. **پیروی کورکورانه از قانون.** «هر تابع حداکثر ۵ خط» یک قانون نیست. قانون واقعی این است: هر تابع یک کار، در یک سطح انتزاع.
5. **تمیز کردن بدون تست.** بازنویسی کد بدون تست ممکن است رفتار را تغییر دهد. اول تست، بعد تمیزکاری (ماژول ۱۱).
6. **فکر کردن اینکه Clean Code فقط برای تیم‌های بزرگ است.** «تیم» شامل خودِ شش ماه بعدِ تو هم هست.

## ۹. Code Review: یک Senior Engineer چه می‌گوید؟

اگر نسخه‌ی بد در یک Pull Request ارسال شود، یک بازبین با تجربه این کامنت‌ها را می‌گذارد. دقت کن که لحن کامنت‌ها **آموزشی و محترمانه** است و هر کامنت «چرا» را توضیح می‌دهد:

> **nit/naming:** `calc`، `o` و `t` نیت را نمی‌گویند. پیشنهاد: `calculateOrderTotal(order)` و `customerTier`.

> **blocking/typing:** `o: any` باعث می‌شود اشتباه تایپی در `items` در زمان کامپایل دیده نشود. لطفاً یک `interface Order` تعریف کن.

> **blocking/business-rule:** نرخ‌های تخفیف و آستانه‌ی ارسال رایگان قاعده‌ی کسب‌وکار هستند. اگر جای دیگری هم تکرار شده باشند، تغییر بعدی ناقص انجام می‌شود. لطفاً به ثابت‌های نام‌دار منتقل کن.

> **suggestion/side-effect:** `console.log` در یک تابع محاسباتی تست‌ها را آلوده می‌کند. لاگ را به لایه‌ی فراخواننده ببر.

> **question:** چرا `==` و نه `===`؟ اگر `t` از query string بیاید رشته است و `'1' == 1` درست درمی‌آید. آیا این عمدی است؟

> **suggestion/tests:** لطفاً برای هر سطح مشتری و برای مرز ۵۰۰٬۰۰۰ تومان (دقیقاً روی مرز و یک تومان بالاتر) تست اضافه کن.

پیشوندهایی مثل `nit` (جزئی، اختیاری)، `blocking` (باید اصلاح شود) و `question` در بسیاری از تیم‌ها رایج‌اند و به نویسنده کمک می‌کنند اولویت‌ها را بفهمد.

## ۱۲. جمع‌بندی

- Clean Code یعنی کدی که **سریع خوانده، درست فهمیده و با اطمینان تغییر داده** شود.
- دلیل اصلی اهمیت آن **اقتصادی** است: کد بارها بیشتر از نوشته شدن خوانده و تغییر داده می‌شود.
- کد تمیز الزاماً کوتاه‌تر، هوشمندانه‌تر یا پر از Design Pattern نیست.
- ابزارهای اصلی: نام‌های گویا، توابع تک‌مسئولیتی، ثابت‌های نام‌دار، نوع‌های دقیق، نبودِ Side Effect پنهان و تست.
- Clean Code مجموعه‌ای از اصول تجربی است، نه قوانین مطلق؛ هدف همیشه **کاهش پیچیدگی** است.

### چک‌لیست خودارزیابی

- [ ] می‌توانم Clean Code را در یک جمله و بدون استفاده از کلمه‌ی «تمیز» تعریف کنم.
- [ ] می‌توانم سه دلیل اقتصادی برای اهمیت Clean Code بیاورم.
- [ ] می‌دانم چرا `any` و اعداد جادویی خوانایی و ایمنی را کم می‌کنند.
- [ ] می‌توانم توضیح دهم چرا نسخه‌ی تمیز این درس طولانی‌تر ولی بهتر است.
- [ ] می‌دانم Clean Code در چه موقعیت‌هایی ارزش کمتری دارد (Prototype، اسکریپت یک‌بارمصرف).
