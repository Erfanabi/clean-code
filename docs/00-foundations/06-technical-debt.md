# درس ۶: بدهی فنی (Technical Debt)

> ماژول ۰۰ — مبانی Clean Code · [فهرست ماژول](README.md) · درس قبل: [نگهداشت‌پذیری](05-maintainability.md) · درس بعد: [بوی کد](07-code-smells.md)

## مقدمه

جمعه شب است، فردا کمپین فروش شروع می‌شود و درگاه پرداخت جدید هنوز کار نمی‌کند. تصمیم می‌گیری نرخ مالیات را مستقیم در سه فایل هاردکد کنی، تست ننویسی و فقط کار را راه بیندازی. این تصمیم **ممکن است درست باشد**. اما چیزی که ساختی یک **وام** است: امروز زمان قرض گرفتی و از فردا هر بار که به این کد دست بزنی، «بهره» می‌پردازی. این درس درباره‌ی همین وام است: چیست، انواعش کدام‌اند، کی گرفتنش عاقلانه است و چطور بازپرداختش کنیم.

## اهداف یادگیری

در پایان این درس باید بتوانم:

- استعاره‌ی بدهی فنی، «اصل» و «بهره»ی آن را توضیح دهم.
- چهار ربع بدهی فنی (Technical Debt Quadrant) را تشخیص دهم.
- منابع رایج بدهی فنی را در یک پروژه شناسایی کنم.
- بدهی فنی را برای مدیر غیرفنی با زبان کسب‌وکار توضیح دهم.
- راهکارهای عملی ثبت، اولویت‌بندی و بازپرداخت بدهی را به کار ببرم.

## ۱. مفهوم اصلی

### تاریخچه و تعریف

Ward Cunningham (خالق اولین Wiki و از نویسندگان Agile Manifesto) در سال ۱۹۹۲ این استعاره را مطرح کرد. ایده‌ی اصلی او این بود: وقتی نرم‌افزاری را با درک **فعلی** خود از مسئله منتشر می‌کنی، مثل این است که وام گرفته‌ای. وام گرفتن بد نیست — به تو اجازه می‌دهد سریع‌تر حرکت کنی و از بازخورد واقعی یاد بگیری. اما اگر بعداً کد را با درک **جدید** خود هماهنگ نکنی، بهره جمع می‌شود.

**بدهی فنی: هزینه‌ی اضافه‌ای که در آینده برای تغییر سیستم می‌پردازیم، به خاطر میان‌برها یا ناهماهنگی‌هایی که امروز در کد وجود دارند.**

### اصل و بهره

Martin Fowler در یادداشت Technical Debt این استعاره را دقیق‌تر کرده است:

- **اصل (Principal):** هزینه‌ی یک‌باره‌ی درست کردن کد. مثلاً ۲ روز برای جمع کردن نرخ مالیات در یک جا و نوشتن تست.
- **بهره (Interest):** هزینه‌ی اضافه‌ای که **هر بار** که به آن بخش از کد دست می‌زنی می‌پردازی. مثلاً هر تغییر مالیاتی به‌جای ۱۰ دقیقه، ۲ ساعت طول می‌کشد چون باید سه فایل را پیدا و هماهنگ کنی.

نکته‌ی کلیدی: **بهره فقط وقتی پرداخت می‌شود که به آن کد دست بزنی.** کد کثیفی که هرگز تغییر نمی‌کند، تقریباً بهره‌ای ندارد. پس اولویت بازپرداخت با بخش‌هایی است که **مرتب تغییر می‌کنند** و **کثیف‌اند**.

### چهار ربع بدهی فنی

Fowler بدهی را روی دو محور دسته‌بندی کرده است: **آگاهانه/ناآگاهانه** (Deliberate/Inadvertent) و **محتاطانه/بی‌پروا** (Prudent/Reckless):

| | بی‌پروا (Reckless) | محتاطانه (Prudent) |
|---|---|---|
| **آگاهانه** | «برای طراحی وقت نداریم.» | «باید الان منتشر کنیم و پیامدهایش را مدیریت می‌کنیم.» |
| **ناآگاهانه** | «لایه‌بندی؟ یعنی چه؟» | «حالا فهمیدیم باید چطور طراحی‌اش می‌کردیم.» |

- **آگاهانه و محتاطانه:** تنها نوع بدهی که می‌تواند **تصمیم مهندسی خوب** باشد. تیم می‌داند چه وامی گرفته، آن را ثبت کرده و برنامه‌ی بازپرداخت دارد.
- **آگاهانه و بی‌پروا:** تیم می‌داند کار اشتباه است ولی بدون برنامه انجامش می‌دهد. این همان «بعداً درستش می‌کنیم» است که هرگز اتفاق نمی‌افتد.
- **ناآگاهانه و بی‌پروا:** ناشی از کمبود دانش. راه‌حل: آموزش (مثل همین بوت‌کمپ!) و Code Review.
- **ناآگاهانه و محتاطانه:** **اجتناب‌ناپذیر.** حتی بهترین تیم‌ها بعد از ساختن سیستم، بهتر می‌فهمند چطور باید طراحی‌اش می‌کردند. این بدهی نشانه‌ی **یادگیری** است، نه شکست.

### منابع رایج بدهی فنی

- کد تکراری (Copy-Paste)
- اعداد و قواعد کسب‌وکار هاردکد شده
- نبودِ تست یا تست‌های شکننده
- وابستگی‌های قدیمی (کتابخانه‌هایی که سال‌ها به‌روز نشده‌اند)
- مستندات قدیمی یا گمراه‌کننده
- طراحی‌ای که با درک فعلی از دامنه هماهنگ نیست
- `any` در TypeScript، `// @ts-ignore` و `// eslint-disable`
- TODOهای قدیمی بدون صاحب

## ۲. توضیح فنی: مدیریت بدهی فنی

### ۱. شفاف کردن (Make it visible)

بدهیِ ثبت‌نشده مدیریت‌نشدنی است. روش‌های رایج:

- **TODO با زمینه:** نه `// TODO: fix`، بلکه:

</div>

```typescript
// TODO(TECH-142): Tax rate is duplicated in invoice.ts and checkout.ts.
// Move to a single TaxPolicy before the 2027 tax update. Owner: payments team.
```

<div dir="rtl">

- **Backlog بدهی:** تیکت‌های مشخص در ابزار مدیریت پروژه با برچسب `tech-debt`، شامل: کجاست، چه بهره‌ای دارد (چقدر ما را کند می‌کند) و هزینه‌ی تخمینی اصل.
- **ADR (Architecture Decision Record):** وقتی بدهی آگاهانه می‌گیری، دلیل و شرایط بازپرداخت را مستند کن.

### ۲. اولویت‌بندی

فرمول ساده‌ی ذهنی: **اولویت = بهره × دفعات تغییر ÷ هزینه‌ی اصل**

- کد کثیف در هسته‌ی پرداخت که هر هفته تغییر می‌کند: اولویت بالا.
- کد کثیف در گزارش‌سازی که سالی یک بار باز می‌شود: اولویت پایین.

ابزار کمکی: بررسی تاریخچه‌ی Git برای یافتن فایل‌هایی که **هم** پرتغییرند (Churn بالا) **و هم** پیچیده‌اند. این تحلیل «Hotspot» نام دارد.

### ۳. بازپرداخت

- **پیوسته (Boy Scout Rule — درس ۱۰):** هر بار که به کدی دست می‌زنی، کمی بهترش کن. ارزان‌ترین روش.
- **همراه فیچر:** وقتی فیچری در یک بخش بدهکار تعریف می‌شود، بازپرداخت را در تخمین همان فیچر بگنجان.
- **بودجه‌ی ثابت:** بعضی تیم‌ها درصد مشخصی از هر Sprint را به بدهی اختصاص می‌دهند.
- **بازنویسی کامل:** آخرین گزینه و پرریسک. معمولاً بازآرایی تدریجی امن‌تر است.

### ۴. صحبت با مدیر

مدیر غیرفنی «کد کثیف» را نمی‌فهمد، اما «هزینه» و «ریسک» را می‌فهمد:

- ❌ «این کد خیلی کثیف است، باید Refactor کنیم.»
- ✅ «هر تغییر قیمت‌گذاری الان ۳ روز طول می‌کشد و در ۶ ماه گذشته ۲ باگ مالی ایجاد کرده. با ۴ روز کار، این زمان به نصف روز می‌رسد. با توجه به اینکه ماهی دو تغییر قیمت داریم، در کمتر از یک ماه سرمایه‌گذاری برمی‌گردد.»

## ۳. مثال اشتباه (Bad Code)

سناریو: نرخ مالیات بر ارزش افزوده (فرض کن ۱۰ درصد) و آستانه‌ی معافیت. برای رسیدن به ددلاین، در سه جای مختلف سیستم هاردکد شده است.

</div>

```javascript
// JavaScript — Bad implementation: debt spread across three files

// checkout.js
export function checkoutTotal(subtotal) {
  return subtotal + subtotal * 0.1;
}

// invoice.js
export function invoiceTax(subtotal) {
  // TODO fix later
  return Math.round(subtotal * 0.10);
}

// admin-report.js
export function reportTax(orders) {
  return orders.reduce((sum, o) => sum + (o.subtotal > 0 ? o.subtotal * 0.1 : 0), 0);
}
```

```typescript
// TypeScript — Bad implementation: debt spread across three files

// checkout.ts
export function checkoutTotal(subtotal: number) {
  return subtotal + subtotal * 0.1;
}

// invoice.ts
export function invoiceTax(subtotal: number) {
  // TODO fix later
  return Math.round(subtotal * 0.10);
}

// admin-report.ts
export function reportTax(orders: any[]) {
  return orders.reduce((sum, o) => sum + (o.subtotal > 0 ? o.subtotal * 0.1 : 0), 0);
}
```

## ۴. تحلیل کد بد

- **دانش تکراری:** «نرخ مالیات ۱۰٪ است» در سه جا و با **سه شکل نوشتاری متفاوت** (`0.1`، `0.10`، داخل ternary) تکرار شده. جست‌وجوی `0.1` ممکن است `0.10` را پیدا نکند.
- **ناهماهنگی پنهان:** فاکتور گرد می‌کند (`Math.round`)، صفحه‌ی پرداخت نه. پس مبلغ مالیات در صفحه‌ی پرداخت و فاکتور **ممکن است چند تومان متفاوت باشد**. این یک باگ مالی واقعی است که مشتری یا حسابرس پیدا می‌کند.
- **رفتار متفاوت در مرزها:** گزارش برای مبلغ منفی (مثلاً سفارش مرجوعی) مالیات صفر حساب می‌کند، ولی Checkout و فاکتور نه. کدام درست است؟ کسی نمی‌داند.
- **TODO بی‌فایده:** `// TODO fix later` نمی‌گوید **چه** چیزی، **چرا**، **کی** و **چه کسی**. این TODO احتمالاً سال‌ها همان‌جا می‌ماند.
- **بهره‌ی واقعی:** وقتی قانون مالیات به ۱۲٪ تغییر کند (که در عمل اتفاق می‌افتد)، باید هر سه جا پیدا و تغییر داده شود. فراموش کردن یکی = گزارش مالی اشتباه.

## ۵. پیاده‌سازی صحیح (Clean Code)

</div>

```typescript
// TypeScript — Clean implementation
// tax-policy.ts — the single source of truth for VAT rules.
export const VAT_RATE = 0.1;

/** Value-added tax for a positive amount, rounded to the nearest Toman. */
export function calculateVat(amountInToman: number): number {
  if (amountInToman <= 0) return 0;
  return Math.round(amountInToman * VAT_RATE);
}

// checkout.ts
import { calculateVat } from './tax-policy';

export function calculateCheckoutTotal(subtotal: number): number {
  return subtotal + calculateVat(subtotal);
}

// invoice.ts
import { calculateVat } from './tax-policy';

export function calculateInvoiceTax(subtotal: number): number {
  return calculateVat(subtotal);
}

// admin-report.ts
import { calculateVat } from './tax-policy';

interface ReportedOrder {
  readonly subtotal: number;
}

export function calculateTotalVat(orders: readonly ReportedOrder[]): number {
  return orders.reduce((sum, order) => sum + calculateVat(order.subtotal), 0);
}
```

```javascript
// JavaScript — Clean implementation
// tax-policy.js
export const VAT_RATE = 0.1;

/**
 * Value-added tax for a positive amount, rounded to the nearest Toman.
 * @param {number} amountInToman
 * @returns {number}
 */
export function calculateVat(amountInToman) {
  if (amountInToman <= 0) return 0;
  return Math.round(amountInToman * VAT_RATE);
}

// checkout.js
import { calculateVat } from './tax-policy.js';

export function calculateCheckoutTotal(subtotal) {
  return subtotal + calculateVat(subtotal);
}
```

### تحلیل پیاده‌سازی صحیح

- **منبع واحد حقیقت (Single Source of Truth):** قاعده‌ی مالیات (نرخ، گرد کردن، رفتار برای مبالغ غیرمثبت) فقط در `tax-policy` تعریف شده است. تغییر نرخ = تغییر یک خط.
- **ناهماهنگی حذف شد:** همه جا از همان تابع استفاده می‌کنند، پس همه جا به یک شکل گرد می‌شود.
- **تصمیم کسب‌وکار صریح شد:** «مالیات مبالغ غیرمثبت صفر است» حالا یک قاعده‌ی نوشته‌شده است، نه اتفاقی در یکی از سه فایل. اگر این قاعده اشتباه باشد، حداقل یک جا برای بحث و اصلاح وجود دارد.
- **قابل تست:** یک مجموعه تست برای `calculateVat` همه‌ی مصرف‌کننده‌ها را پوشش می‌دهد.
- **گام بعدی محتمل:** اگر نرخ مالیات بر اساس دسته‌ی کالا متفاوت شود، فقط `tax-policy` باید تغییر کند. Locality از درس قبل.

**آیا بدهی اولیه اشتباه بود؟** نه لزوماً. اگر تیم آگاهانه برای ددلاین آن را گرفته و **ثبت** کرده بود (بدهی آگاهانه و محتاطانه)، تصمیم معقولی بود. اشتباه، رها کردنش با `// TODO fix later` بود.

## ۶. مقایسه‌ی دو پیاده‌سازی

| معیار | Bad Code | Clean Code |
|---|---|---|
| تعداد جاهای تعریف نرخ | ۳ (با سه شکل نوشتاری) | ۱ |
| هماهنگی گرد کردن | ناهماهنگ؛ باگ مالی | یکسان |
| تغییر نرخ مالیات | جست‌وجو و تغییر چند فایل، ریسک فراموشی | یک خط |
| مستند بودن قاعده‌ی مبالغ منفی | تصادفی در یک فایل | صریح در یک تابع |
| بهره‌ی هر تغییر | بالا | تقریباً صفر |

## ۷. کاربرد در پروژه‌های واقعی

- **Frontend:** نسخه‌های قدیمی React یا کتابخانه‌های UI که به‌روز نشده‌اند، رایج‌ترین بدهی‌اند. هر نسخه‌ای که عقب بمانی، به‌روزرسانی بعدی گران‌تر می‌شود (بهره‌ی مرکب!).
- **Next.js:** مهاجرت از Pages Router به App Router نمونه‌ی کلاسیک بدهی «ناآگاهانه و محتاطانه» است: کد قدیمی در زمان خودش درست بود، ولی حالا با پلتفرم هماهنگ نیست.
- **TypeScript:** هر `any` یک وام کوچک است. ابزارهایی مثل قانون `@typescript-eslint/no-explicit-any` آن‌ها را شفاف می‌کنند.
- **Backend:** نبودِ تست برای منطق پرداخت. هر تغییر در آن، به خاطر ترس از شکستن، کند و پراسترس است — بهره‌ی روانی هم بهره است.

## ۸. اشتباهات رایج

1. **همه‌ی کدهای بد را «بدهی فنی» نامیدن.** کد کثیفی که از بی‌دقتی آمده، بدهی «بی‌پروا» است؛ نباید با استعاره‌ی وام توجیهش کرد.
2. **باور به اینکه هر بدهی‌ای بد است.** بدهی آگاهانه و محتاطانه ابزار مشروع کسب‌وکار است.
3. **TODO بدون زمینه.** TODO بدون شناسه، دلیل و صاحب، فقط نویز است.
4. **بازپرداخت بدهی در کدی که تغییر نمی‌کند.** بهره‌ای ندارد؛ وقت را جای دیگر خرج کن.
5. **بازنویسی کامل به‌جای بازآرایی تدریجی.** بازنویسی کامل معمولاً بیش از برآورد طول می‌کشد و باگ‌های قبلاً حل‌شده را برمی‌گرداند.
6. **صحبت فنی با مدیر.** به زبان زمان، هزینه و ریسک صحبت کن.

## ۹. Code Review: دیدگاه Senior Engineer

یک Senior لزوماً PR حاوی بدهی را رد نمی‌کند، اما **شفافیت** می‌خواهد:

> **question:** می‌بینم نرخ مالیات اینجا هاردکد شده و در `checkout.ts` هم هست. اگر این برای ددلاین فرداست، مشکلی نیست — ولی لطفاً یک تیکت بساز و TODO را با شناسه‌ی تیکت و توضیح به‌روز کن. اگر وقت هست، استخراج `calculateVat` حدود ۲۰ دقیقه کار است و همین الان ناهماهنگی گرد کردن را هم رفع می‌کند.

> **blocking/bug:** فاکتور مالیات را گرد می‌کند ولی Checkout نه. این یعنی مبلغ نمایش‌داده‌شده به مشتری و مبلغ فاکتور می‌تواند متفاوت باشد. این را حتی با ددلاین هم نمی‌شود منتشر کرد.

دقت کن که Senior بین «بدهی قابل‌قبول با ثبت» و «باگی که نباید منتشر شود» تمایز قائل شده است.

## ۱۱. جمع‌بندی

- بدهی فنی استعاره‌ی Ward Cunningham است: میان‌بر امروز = وام؛ هزینه‌ی اضافه‌ی هر تغییر = بهره.
- بهره فقط وقتی پرداخت می‌شود که به آن کد دست بزنی؛ پس بخش‌های پرتغییر و کثیف اولویت دارند.
- چهار ربع: آگاهانه/ناآگاهانه × محتاطانه/بی‌پروا. فقط «آگاهانه و محتاطانه» یک انتخاب مهندسی سالم است.
- مدیریت: شفاف کن (تیکت، TODO با زمینه)، اولویت‌بندی کن (Hotspot)، پیوسته بازپرداخت کن (Boy Scout).
- با مدیر به زبان هزینه، زمان و ریسک صحبت کن.

### چک‌لیست خودارزیابی

- [ ] می‌توانم اصل و بهره را با یک مثال از کار خودم توضیح دهم.
